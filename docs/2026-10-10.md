# 2026-10-10 — Launch-Aware Evaluation and RAID Setup

## Decisions made

- The target variable is weekly `Customer Orders` aggregated across all distribution centers for the aggregate experiments.
- Evaluation is launch-aligned: each target SKU's forecast origin is its recorded launch/start week.
- The primary forecast window is **13 weeks**, representing approximately one quarter.
- A target SKU's own demand is unavailable to the forecasting method at launch and must not be used as input.
- Donor SKUs must have launched **strictly before** the target SKU's forecast origin.
- Donor demand observations must be from weeks **strictly before** the target origin.
- Retrieval metadata are `Product Offering`, `Generation`, and `ASP Group`.
- For the primary evaluation, a target SKU must have observed actual demand for the complete 13-week forecast window.
- The same eligible target SKUs and forecast windows should be used to compare RAID, RAID + Sundial, and GAT + Sundial.
- The current configuration is for the **aggregate** setting. Distribution-center experiments will need a corresponding configuration, with distribution center included as context.
- `start` defines launch timing and evaluation origin; lifecycle `end` is not a retrieval feature.
- Missing target demand is not silently imputed as zero.

## Configuration and launch-evaluation loader

Created:

- `configs/intel_sku/aggregate_launch_evaluation.json`
- `scripts/data/load_launch_evaluation_data.py`

The JSON configuration specifies input paths, target column, 13-week forecast window, retrieval features, eligibility rules, and output artifact names.

The loader:

1. Loads and validates the aggregate demand data and SKU metadata.
2. Creates launch-aligned evaluation cases.
3. Determines which previously launched SKUs have at least one non-missing historical demand observation before each target's origin.
4. Separates eligible cases from excluded cases and records exclusion reasons.
5. Provides `get_donor_history(...)` to retrieve donor observations strictly before the origin, without the target SKU's demand.
6. Provides `get_target_actuals(...)` separately for scoring.
7. Writes evaluation cases, exclusions, and a JSON summary.

Run from the repository root:

```bash
python scripts/data/load_launch_evaluation_data.py
```

The reason counts sum to 29 because two late-launching SKUs have both `forecast_window_exceeds_dataset` and `incomplete_target_forecast_window`. There are **27 excluded SKUs**, not 29.

### Interpreting exclusions

- SKUs launching in week 1 have no earlier history in the dataset and cannot be evaluated under the launch-aligned protocol.
- `forecast_window_exceeds_dataset` means that the 13-week window starting at the SKU's launch extends beyond week 187.
- `incomplete_target_forecast_window` means fewer than 13 weekly actual-demand observations are available within the target's forecast window. This can happen because the window extends beyond the dataset or because weeks within the dataset have missing demand.
- `SKU-G-5` and `SKU-I-5` launch in week 179. Their forecast windows are weeks 179–191, while the dataset ends at week 187; therefore, only nine weeks fall within the dataset.
- The two late-launching SKUs are `SKU-G-5` and `SKU-I-5`.

### Evaluation-case fields

The case file includes the target SKU, forecast origin, forecast-window boundaries, number of previously launched SKUs, number of donor candidates with historical observations, and number of target actual weeks available. The donor-candidate count is **not** the number of neighbors RAID ultimately selects.


The generated split uses seed `42` and records:

| Item | Count |
|---|---:|
| Total SKUs | 86 |
| Evaluation-ineligible SKUs assigned to training | 27 |
| Eligible SKUs assigned to training | 24 |
| Total training SKUs | 51 |
| Test SKUs | 35 |

Artifacts are written to:

```text
artifacts/Intel_SKU/splits/raid_aggregate/
```

**Protocol caveat:** This is a SKU-held-out cold-start simulation, not strict historical backtesting. Training labels for training SKUs may occur after some test SKUs' launch origins. For every test forecast, target-SKU labels are held out and donor histories are restricted to weeks strictly before that test SKU's launch. A strict historical claim would require origin-specific training cutoffs and would not satisfy the requirement that all 27 evaluation-ineligible SKUs always belong to training.

The updated training script is intended to save the best and final checkpoints, per-epoch loss and timing history, configuration snapshots, and run metadata. The best checkpoint is selected by **training loss**, not validation loss; that selection alone does not establish generalization.

The implementation is **paper-guided, not verified as an exact reproduction** of RAID. In particular, the displayed paper objective and fast inference sampler leave details that require documented implementation assumptions. The implementation has passed a synthetic forward/loss/backward smoke test, but the full pipeline has not yet been verified on the Intel dataset.

### Interpretation and validation status

The train/evaluate pipeline has run end-to-end, but the RAID baseline is **not yet validated as a useful forecasting method**. WAPE is approximately 99.89%, and sMAPE is approximately 195.72% under the evaluator's formula. These results indicate poor aggregate accuracy and warrant investigation.

Before treating this as a final baseline, perform these checks:

1. Inspect predictions and actuals for several individual test SKUs.
2. Check whether predictions are negative, extreme, nearly constant, or otherwise implausible.
3. Compare RAID with simple baselines, including a nearest-neighbor donor forecast and a donor-history mean/shape-and-scale forecast.
4. Review the loss implementation and the relative scales of `diffusion_loss`, `base_loss`, and `final_loss`.
5. Verify metric implementation and aggregation, and report per-SKU as well as pooled metrics.

The evaluation protocol remains SKU-held-out cold-start simulation, **not strict historical backtesting**. The current run proves that the scripts execute and produce artifacts; it does not establish that the implementation is faithful to the original RAID code or that its predictions generalize well.

## RAID + Sundial: next experiment

The next experiment is a **RAID + Sundial adaptation**, with Sundial frozen. It is not an exact reproduction of RAID or Sundial's original evaluation.

Intended high-level pipeline:

```text
Target SKU metadata
        |
        v
Frozen BGE-M3 metadata embeddings
        |
        v
RAID retrieval / neighbor weighting
        |
        v
Construct a target-specific pseudo-history using eligible donor histories
        |
        v
Frozen Sundial
        |
        v
13-week forecast at the target launch origin
        |
        v
Same test SKUs and metrics as RAID
```

Protocol constraints:

- Keep the same 51/35 SKU split and the same 35 eligible test SKUs.
- Use the same launch origin and 13-week forecast window as the RAID evaluation.
- Donors must have launched strictly before the target's origin.
- Only donor observations from weeks strictly before the origin may be used.
- Do not pass the target SKU's demand history to the forecasting model.
- Do not use lifecycle `end` as a retrieval feature.
- Keep Sundial frozen; do not fine-tune it on the Intel test targets.
- Use the same actuals and metric definitions as RAID for comparison.
- Document how pseudo-history is formed and how its length is adapted to Sundial's input interface.

**Implementation detail to resolve before coding:** the current RAID evaluator calls RAID to generate a 13-week forecast. That output is not automatically a historical context for Sundial. The RAID + Sundial experiment must explicitly define a pseudo-history from pre-origin donor data (or specify and justify another construction) so Sundial forecasts the correct target window rather than accidentally forecasting a second horizon after the target window. Check the released Sundial inference interface for supported context lengths before deciding whether padding, truncation, or a longer donor-history construction is needed.
