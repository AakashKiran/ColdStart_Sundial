# 2026-10-09 - Intel SKU Data Preprocessing

## Objective

Implement a reproducible preprocessing pipeline for the Intel SKU dataset. The script validates the original data, prepares aggregate and distribution-center-level datasets, and saves a validation summary.

**Script:** `scripts/preprocessing/prepare_intel_sku.py`

**Command:** 
- Ensure sundial environment is active (`conda activate sundial`)
- `python scripts/preprocessing/prepare_intel_sku.py` from repository root

## 1. Input datasets

The script reads the following files from `data/Intel_SKU/raw/`:

- `msom.2020.0933.csv`
- `Intel_actual_demand.csv`
- `startend_date.csv`

## 2. Preprocessing and validation

The script performs the following operations:

1. Loads the three raw datasets and validates their required columns.
2. Standardizes SKU identifiers for matching across files.
3. Checks SKU consistency across the source, aggregate demand, and lifecycle datasets.
4. Checks for duplicate source keys, missing or negative demand/forecast values, inconsistent static attributes, and invalid lifecycle boundaries.
5. Converts aggregate demand from wide format to long format.
6. Verifies that aggregate `Customer Orders` agrees with the sums calculated from the original source.
7. Constructs a complete distribution-center × SKU × week panel without automatically imputing missing demand.
8. Saves the processed datasets and a JSON validation summary.

## 3. Processed output files

### A. Aggregate-level data

Directory: `data/Intel_SKU/processed/aggregate/`

**`aggregate_sku_weekly_demand.csv`**

- One row per SKU-week, with columns `sku`, `week`, and `customer_orders`.
- Contains 16,082 rows, corresponding to 86 SKUs × 187 weeks.
- Preserves missing aggregate demand values as missing.

**`sku_metadata.csv`**

- One row per SKU, containing `sku`, `Product Offering`, `Generation`, `ASP Group`, `start`, and `end`.
- Combines static product attributes from the original source with lifecycle boundaries from `startend_date.csv`.
- Contains 86 rows.

### B. Distribution-center-level data

Directory: `data/Intel_SKU/processed/by_distribution_center/`

**`distribution_center_observations.csv`**

- Preserves the 26,114 recorded source observations.
- Contains distribution center, SKU, week, `customer_orders`, `forecasted_demand`, static product attributes, and `source_record_present`.
- Represents only combinations for which a source record exists.

**`distribution_center_weekly_panel.csv`**

- Contains the complete distribution-center × SKU × week grid.
- Contains 80,410 rows, corresponding to 5 distribution centers × 86 SKUs × 187 weeks.
- Retains missing demand and forecast values for combinations without a source record; no zero imputation is performed.

## 4. Additional columns

The following columns are constructed during preprocessing:

- **`sku_key`**: A normalized SKU identifier used internally to match SKU IDs across the input datasets despite punctuation differences.
- **`source_record_present`**: Boolean indicator showing whether the center-SKU-week combination had a corresponding row in the original source. `True` indicates that a row exists; `False` indicates that it does not.
- **`record_status`**: Categorizes each row in the complete panel as:
  - `observed`: A source record exists.
  - `missing_within_lifecycle`: No source record exists, and the week falls within the recorded SKU lifecycle.
  - `outside_lifecycle`: No source record exists, and the week falls outside the recorded SKU lifecycle.

An absent source record is not automatically interpreted as zero demand. The status labels describe source-record coverage relative to the recorded lifecycle dates; they do not establish actual demand.

## 5. Validation artifact

The script writes `artifacts/Intel_SKU/preprocessing/validation_summary.json`. It records dataset dimensions, SKU and distribution-center coverage, aggregate consistency results, panel coverage, and validation outcomes.

This artifact provides a reproducible summary of the preprocessing run and makes it easier to detect unexpected changes in future runs.
